Apache XTable PoC: Convert One Hudi Table Into Delta and Iceberg Metadata

A practical, from-scratch demo you can use in a presentation to explain how Apache XTable exposes the same lakehouse data through multiple table formats.

Apache XTable is a cross-table converter for lakehouse table formats. In plain language, it helps teams write data in one format, such as Apache Hudi, and make that same table readable through other formats, such as Delta Lake and Apache Iceberg.

This tutorial implements three short PoCs that work well in a presentation:

PoC 1 Hudi to Delta and Iceberg metadata conversion.
PoC 6 Show that the conversion is metadata-focused, not a full data copy.
PoC 9 Run the same aggregate query and compare results.
Recommended demo path: run this locally with Docker first. Your homelab k3s cluster is useful if you want to add MinIO and make the demo look closer to production, but local Docker is easier to rehearse and safer for a live presentation.

Architecture

The demo starts with a small Hudi table called sales. XTable then generates Delta and Iceberg metadata next to the existing data files.

/lakehouse /hudi/sales .hoodie/ Hudi metadata region=BR/*.parquet region=DE/*.parquet region=US/*.parquet _delta_log/ Delta metadata generated by XTable metadata/ Iceberg metadata generated by XTable

That file tree is the main visual for the presentation. The Parquet files are the physical data. XTable adds table-format metadata so other engines can understand the same dataset.

Prerequisites

Install these tools on your machine:

  • docker
  • git
  • unzip
  • java 11 (required by the local XTable build)

Apache XTable's README recommends Java 11 for building the project. The README also documents the bundled jar workflow and the YAML configuration used by the converter.

Validate Docker access before starting:

docker ps
If Docker reports permission denied for /var/run/docker.sock: add your user to the Docker group with sudo usermod -aG docker "$USER", then log out and back in (or run newgrp docker). Confirm the fix with docker ps. Avoid making the Docker socket world-writable.

Setup From Scratch

Create a working directory:

mkdir xtable-poc
cd xtable-poc
mkdir lakehouse scripts xtable-config

# The Spark image runs as a non-root user and must write table files here.
chmod 0777 lakehouse

Clone and build Apache XTable:

git clone https://github.com/apache/incubator-xtable.git
cd incubator-xtable
./mvnw install -DskipTests
cd ..

Locate and validate the executable utilities jar:

XTABLE_JAR="$(find incubator-xtable/xtable-utilities/target \
  -name 'xtable-utilities_*-bundled.jar' -print -quit)"

test -n "$XTABLE_JAR" || {
  echo "XTable utilities bundled jar was not found. Build XTable first." >&2
  exit 1
}

unzip -p "$XTABLE_JAR" META-INF/MANIFEST.MF | grep 'Main-Class'

The output must include Main-Class: org.apache.xtable.utilities.RunSync. XTable builds several bundled jars, but only the xtable-utilities jar is the command-line converter used in this tutorial.

Create The Hudi Source Table

Create scripts/create_hudi_sales.py:

from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("create-hudi-sales")
    .config("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
    .getOrCreate()
)

data = [
    (1, "BR", "2026-07-01", 100.50),
    (2, "BR", "2026-07-01", 220.00),
    (3, "US", "2026-07-02", 80.25),
    (4, "US", "2026-07-02", 140.00),
    (5, "DE", "2026-07-03", 99.99),
]

df = spark.createDataFrame(data, ["sale_id", "region", "sale_date", "amount"])

table_path = "/lakehouse/hudi/sales"

(
    df.write.format("hudi")
    .option("hoodie.table.name", "sales")
    .option("hoodie.datasource.write.recordkey.field", "sale_id")
    .option("hoodie.datasource.write.precombine.field", "sale_date")
    .option("hoodie.datasource.write.partitionpath.field", "region")
    .option("hoodie.datasource.write.hive_style_partitioning", "true")
    .option("hoodie.datasource.write.table.type", "COPY_ON_WRITE")
    .mode("overwrite")
    .save(table_path)
)

spark.stop()

Run the Spark job in Docker:

docker run --rm \
  -e HOME=/tmp \
  -e HADOOP_USER_NAME=spark \
  -v "$PWD/lakehouse:/lakehouse" \
  -v "$PWD/scripts:/scripts:ro" \
  apache/spark:3.5.1 \
  /opt/spark/bin/spark-submit \
  --conf spark.jars.ivy=/tmp/.ivy2 \
  --packages org.apache.hudi:hudi-spark3.5-bundle_2.12:0.15.0 \
  /scripts/create_hudi_sales.py
Why set the Ivy path? The default Spark image may not have a writable /home/spark/.ivy2 directory. Using /tmp/.ivy2 prevents the dependency-resolution FileNotFoundException. Do not add a numeric --user here: Hadoop login can fail when that UID has no entry in the container's /etc/passwd.

Inspect the table:

find lakehouse/hudi/sales -maxdepth 3 -type d | sort
find lakehouse/hudi/sales -name '*.parquet'

At this point, you should have a Hudi table with a .hoodie directory and Parquet data files partitioned by region.

PoC 1: Convert Hudi To Delta And Iceberg Metadata

Create xtable-config/sales.yml:

sourceFormat: HUDI
targetFormats:
  - DELTA
  - ICEBERG
datasets:
  -
    tableBasePath: /lakehouse/hudi/sales
    tableName: sales
    namespace: demo
    partitionSpec: region:VALUE

Run XTable:

XTABLE_JAR="$(find incubator-xtable/xtable-utilities/target \
  -name 'xtable-utilities_*-bundled.jar' -print -quit)"

test -n "$XTABLE_JAR" || {
  echo "XTable utilities bundled jar was not found. Build XTable first." >&2
  exit 1
}

docker run --rm \
  -v "$PWD/lakehouse:/lakehouse" \
  -v "$PWD/xtable-config:/xtable-config:ro" \
  -v "$PWD/$XTABLE_JAR:/xtable.jar:ro" \
  eclipse-temurin:11 \
  java -jar /xtable.jar \
  --datasetConfig /xtable-config/sales.yml

Now inspect the table again:

find lakehouse/hudi/sales -maxdepth 2 -type d | sort

You should now see directories similar to this:

lakehouse/hudi/sales/.hoodie
lakehouse/hudi/sales/_delta_log
lakehouse/hudi/sales/metadata
lakehouse/hudi/sales/region=BR
lakehouse/hudi/sales/region=DE
lakehouse/hudi/sales/region=US

This is the first key result: XTable generated metadata for Delta and Iceberg from a Hudi source table.

PoC 6: Prove This Is Metadata-Focused

The best way to explain XTable is to show the physical files. Run: 

find lakehouse/hudi/sales -maxdepth 3 -type f | sort

Point out the file groups:

.hoodie/*              Hudi metadata
_delta_log/*.json      Delta transaction log
metadata/*.json        Iceberg table metadata
region=*/...parquet    Shared physical data files

Then compare sizes:

du -sh lakehouse/hudi/sales
du -sh lakehouse/hudi/sales/.hoodie
du -sh lakehouse/hudi/sales/_delta_log
du -sh lakehouse/hudi/sales/metadata

The presentation message is simple: XTable does not create three full copies of the table. The data files remain shared. XTable creates target-format metadata so different engines can interpret the same table.

PoC 9: Query Comparison

For the query comparison, run the same aggregate query through Hudi and Delta. The result should match.

Query The Hudi Source Table

Create scripts/query_hudi.py:

from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("query-hudi")
    .config("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
    .getOrCreate()
)

df = spark.read.format("hudi").load("/lakehouse/hudi/sales")
df.createOrReplaceTempView("sales")

spark.sql("""
    SELECT region, COUNT(*) AS sale_count, ROUND(SUM(amount), 2) AS total_amount
    FROM sales
    GROUP BY region
    ORDER BY region
""").show(truncate=False)

spark.stop()

Run it:

docker run --rm \
  -e HOME=/tmp \
  -e HADOOP_USER_NAME=spark \
  -v "$PWD/lakehouse:/lakehouse" \
  -v "$PWD/scripts:/scripts:ro" \
  apache/spark:3.5.1 \
  /opt/spark/bin/spark-submit \
  --conf spark.jars.ivy=/tmp/.ivy2 \
  --packages org.apache.hudi:hudi-spark3.5-bundle_2.12:0.15.0 \
  /scripts/query_hudi.py

Expected result:

+------+----------+------------+
|region|sale_count|total_amount|
+------+----------+------------+
|BR    |2         |320.5       |
|DE    |1         |99.99       |
|US    |2         |220.25      |
+------+----------+------------+

Query Through Delta Metadata

Create scripts/query_delta.py:

from pyspark.sql import SparkSession

spark = (
    SparkSession.builder
    .appName("query-delta")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .getOrCreate()
)

df = spark.read.format("delta").load("/lakehouse/hudi/sales")
df.createOrReplaceTempView("sales")

spark.sql("""
    SELECT region, COUNT(*) AS sale_count, ROUND(SUM(amount), 2) AS total_amount
    FROM sales
    GROUP BY region
    ORDER BY region
""").show(truncate=False)

spark.stop()

Run it:

docker run --rm \
  -e HOME=/tmp \
  -e HADOOP_USER_NAME=spark \
  -v "$PWD/lakehouse:/lakehouse" \
  -v "$PWD/scripts:/scripts:ro" \
  apache/spark:3.5.1 \
  /opt/spark/bin/spark-submit \
  --conf spark.jars.ivy=/tmp/.ivy2 \
  --packages io.delta:delta-spark_2.12:3.2.0 \
  /scripts/query_delta.py

The output should match the Hudi query. That is your clean closing proof: the same source data can be read through another table format after XTable generates the required metadata.

About Iceberg querying: for a short live demo, I would show Iceberg metadata generation rather than make Iceberg querying the risky part. Querying Iceberg live usually means configuring a Spark Iceberg catalog correctly. That is doable, but it adds setup that can distract from the core XTable story.

Optional k3s Homelab Version

If you want to use your homelab k3s cluster, use it to show a more realistic lakehouse shape:

k3s MinIO S3-compatible object storage Spark job creates Hudi table Kubernetes Job runs Apache XTable Spark query job validates Hudi and Delta reads

The flow is:

  1. Deploy MinIO in k3s.
  2. Create a bucket such as lakehouse.
  3. Write the Hudi table to s3a://lakehouse/hudi/sales.
  4. Run XTable as a Kubernetes Job using the same YAML config, but with S3 paths.
  5. Run Spark query jobs against the generated metadata.

This is closer to production, but it introduces S3 credentials, Hadoop S3A configuration, service endpoints, and Kubernetes manifests. For a first presentation, I would keep this as an architecture slide and use the local Docker demo live.

Presentation Script

Use this sequence during the presentation:

  1. Show the Hudi table folders.
  2. Run the Hudi aggregate query.
  3. Run XTable with the YAML config.
  4. Show the new _delta_log and metadata directories.
  5. Run the Delta aggregate query.
  6. Show that the results match.

Useful commands to keep ready:

find lakehouse/hudi/sales -maxdepth 2 -type d | sort
find lakehouse/hudi/sales -maxdepth 3 -type f | sort
du -sh lakehouse/hudi/sales
du -sh lakehouse/hudi/sales/_delta_log
du -sh lakehouse/hudi/sales/metadata

Close with this sentence:

Apache XTable lets us keep one physical dataset while exposing it through multiple lakehouse table formats. That reduces format lock-in and makes it easier for different engines and teams to work with the same data.
